# Infinite Props (`infinite-props`)

A portable binary format and open-source toolchain for **seed-based procedural
2D assets**: one small file encodes the complete recipe for an asset, and a
runtime executes it to produce pixels — deterministically, on any platform.

One `.iprop` file can generate **many reproducible variations** from its seed,
variant, archetype and input uniforms. The asset determines which inputs
change its appearance; different inputs need not produce different images.

This checkout implements stages 1–2 of product **0.7.0** / source language **0.7**
in development: exact integer min/max/clamp, stable vector normalization and
typed immutable asset constants visible in draw and helpers.
The binary format is **0.6**, C API **0.3** and C ABI / SONAME **0.4**. These
are independent contracts. The runtime reads formats 0.1–0.6; the compiler
writes the oldest required format, from 0.4 to 0.6. Later 0.7 stages are pending.

Start with the [language handbook](docs/language/index.md), the
[C API integration guide](backends/capi/README.md) or the
[0.7 migration and implementation notes](docs/language/migration-v0.7.md).

## 1. Vision

A procedural asset recipe can live in application-specific source code,
with placement, collision and emission metadata handled separately from
the pixels.

Infinite Props turns that recipe into a **portable, self-contained, binary
artifact**:

```
source (.ips) ── compiler ──▶ asset.iprop ── interpreter/backend ──▶ pixels
```

The `.iprop` file contains binary instructions executed by a small virtual
machine. The same file runs in the browser, through the C API, and in the
SFML and Godot integrations, producing the same pixels for the same inputs.
Dedicated OpenGL and Vulkan hosts remain planned work.

## 2. Goals

- Define a versioned binary format (`.iprop`) for procedural 2D sprite assets.
- Provide a human-writable language (`.ips`) that compiles to that format.
- Provide a reference CPU interpreter written in C++20.
- Provide a stable C API as the shared foundation every native host links.
- Provide backends for HTML5 (WASM), SFML and Godot (GDExtension), with
  OpenGL and Vulkan hosts planned.
- Provide authoring and inspection tools through the VS Code extension.
- Provide a website with live examples, documentation and installation guides.
- Require bit-exact, cross-platform output for identical programs and all
  generation inputs.
- Bound execution through bytecode validation, fuel budgets and checked
  canvas access, including in the browser.

## 3. Non-goals

- 3D geometry, meshes or SDF output. The format targets 2D raster sprites only.
- Vector path export (may be revisited after v1).
- Runtime loading of parts from separate files ("bundles"). Parts are linked
  at compile time; runtime bundles are a possible post-v1 extension.
- Executing arbitrary programs on the GPU. Planned GPU hosts would present
  images generated by the CPU interpreter (see §8).
- Making the core depend on a specific game engine. Engine adapters consume
  the C API; the core remains independent of them.

## 4. Requirements terminology

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD",
"SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be
interpreted as described in RFC 2119.

The frozen specifications under `spec/` define the binary and VM contracts.
This README is an overview of the current implementation and its goals; the
language handbook defines the supported source syntax.

## 5. The `.iprop` binary format

The format is a contract, not an implementation detail. All interpreters MUST
implement its frozen semantics; the reference interpreter and conformance
suite enforce them. [Format 0.6](spec/iprop-v0.6.md) inherits the frozen
[0.5 contract](spec/iprop-v0.5.md) and defines the stage 1 additions.

### 5.1 Header

- Magic bytes: `IPRP` (4 bytes), followed by the version, flags, section count
  and reserved field in a 20-byte header.
- Header flags identify debug information and the compressed container.
- Frozen format semantics MUST remain unchanged. New opcodes and sections
  require a compatible format version; old interpreters MUST reject files
  they cannot fully honour. The 0.4 compressed envelope may contain a 0.6
  executable, whose version is checked after expansion.

### 5.2 Sections

| Section   | Required | Contents |
| --------- | -------- | -------- |
| `meta`    | yes      | Canvas size, origin, optional emission metadata, variant/archetype counts, fuel budget and declared input/output signature |
| `const`   | yes      | Constant pool: integers, floats, colours, strings |
| `code`    | yes      | Instruction stream and function table, including `draw(variant, archetype)` |
| `debug`   | no       | Symbol names and a source map (`.ips` line → instruction offset); strippable without changing behaviour |
| `parts`   | for parts in format 0.5 | Part instance names and parents; each import alias path identifies an instance |

### 5.3 Metadata

The file carries its rendering metadata and typed declarations inline:

- `size` — canvas dimensions (pixels).
- `origin` — the point used for placement.
- Optional binary `emission` metadata — offset, radius and colour.
- `variants`, `archetypes` — counts exposed to the interpreter.
- `fuel` — the maximum instruction budget for one generation (see §6).

The current `.ips` declarations are `size`, `origin`, `variants`, `archetypes`,
`input`, `output` and `palette`, plus draw/helpers. Collision shapes and
additional anchors are named structured outputs, rather than fixed collider
metadata. The compiler supplies a default fuel budget of 2,000,000;
embedding hosts can override it. Source syntax does not declare `fuel` or
fixed emission metadata.

A `.iprop` file MUST be fully self-contained: no external resources, code or
configuration are needed to execute it. Imported parts (see §7.3) are linked
into the file at compile time, so self-containment holds for composed assets
too.

### 5.4 Input/output model

The format declares an explicit, typed I/O signature in the `meta` section.
Generation is a pure function of its inputs: identical inputs MUST produce
identical outputs — both the image and every structured output.

**Inputs**

| Input | Type | Notes |
| ----- | ---- | ----- |
| `seed` | u32 | initializes the root RNG stream; tools default to 0 |
| `variant` | u32 | validated against `meta.variants` |
| `archetype` | u32 | validated against `meta.archetypes` |
| `size` | u32×u32 | optional requested dimensions; zero uses the asset's declared size |
| uniforms | declared | `color`, `f32` and `u32` binary inputs with defaults; source also supports signed `input i32` using U32 bit patterns |

Generation has no implicit clock or animation state. Its result depends on
the supplied inputs, including any declared uniforms. A host may drive
animation by changing those inputs, for example deriving a seed per frame.

**Outputs**

- `image` — the RGBA canvas; implicit and always present.
- Structured outputs — named slots declared in `meta` and written by
  `draw(...)`:
  - `point` (x, y) — named anchors and attachment points: entrances,
    chimneys, sockets, or the eyes and mouth of a generated portrait.
  - `rect` (x, y, w, h) — collision blocks, such as a computed rock or
    crater collider.
  - `circle` (x, y, r) — round collision shapes.
  - A slot may be singular or a list (`output list rect colliders`).
- The **name is the contract**: output semantics are defined per asset kind
  (`collider`, `bowl`, `eyes`, `hatAnchor`, ...), not by the format.

**Generation model** (concrete API signatures differ by backend):

```
result = generate(file, { seed, variant, archetype, size, uniforms })
        → { image, outputs: { collider, anchors, ... } }
```

Structured outputs are part of the determinism contract and of the
conformance suite (see §9).

In composed assets, a parent MAY read the structured outputs of its parts and
MAY assign them to its own declared outputs, so a child's computed anchor can
surface in the final `outputs` map (see §7.3).

### 5.5 Deterministic layout

- Endianness and instruction encoding are pinned: little-endian values and
  fixed-width, 4-byte instructions in the current formats.
- The constant pool and instruction stream MUST be byte-for-byte
  deterministic: repeating a compilation with the same compiler, source,
  imports and options MUST produce the identical file.

## 6. The virtual machine

The format's execution model is an **imperative stack machine** with
structured control flow and bounded execution resources.

### 6.1 Structure

- Value stack, locals, and a call stack of functions.
- **Structured control flow only**: `block`, `loop`, `if/else`, `br`, `br_if`.
  Arbitrary jumps MUST NOT exist; this keeps validation and analysis simple.
- A fuel counter: instructions, canvas visits and specified sampling work
  consume fuel; exhaustion aborts generation with a defined error. The
  effective budget is `meta.fuel` or the host's override. Loops need not be
  statically bounded, but execution cannot continue after fuel runs out.

### 6.2 Types

- Stack/local values are `i32`, `f32` (IEEE-754 binary32), `color` (RGBA8),
  `vec2` and `distribution`. Unsigned bit patterns travel in integer slots;
  strings in the constant pool name declarations and are not runtime values.
- Control-flow conditions require `i32`. Float comparisons return `i32` 0/1
  and may control a branch; a bare float condition is rejected.

### 6.3 Memory model

- Mutable state consists of the canvas, output slots, stacks/locals, RNG
  streams and part-output registers.
- There is no arbitrary linear-memory access. Every canvas write is checked;
  off-canvas pixel writes are no-ops, while invalid geometry/resource requests
  can trap.

### 6.4 Canvas operations

The VM exposes raster painting primitives, with semantics pinned in the
specification:

- `pixel`, `rect`, `poly`, `line`, `oval` — raster primitives.
- The **alpha compositing rule** is specified exactly, including preservation
  of the destination alpha when compositing translucent colours.
- `weather` — seeded per-pixel wear, preserving alpha, silhouette and bright
  emissive pixels.

### 6.5 Seeded primitives

The RNG and noise are **specification-pinned instructions**, not library
calls, because bit-exact parity across platforms is a core requirement:

- `hash` — splitmix32-style integer hash.
- `unit`, `range`, `index` — draws from a Weyl-sequence stream
  (`state += 0x9e3779b9`, hashed, scaled to `[0,1)`).
- `lo to hi` draws a uniform value with both bounds included: `i32` for two
  integer bounds (rejection sampling, no modulo bias), otherwise `f32`.
  Bounds evaluate once, lower first; reversed or non-finite bounds trap.
  Two colors or two `vec2` values give one random position on the gradient
  or segment between them. `lo to hi with d` draws from a `gaussian`,
  `triangular` or `beta`
  distribution restricted to the range; `distribution` values can be stored
  and passed to and returned from helpers.
- `pick(n)` is an alias for `index(n)`. `pick(a, b, …)` eagerly evaluates
  all choices once, in signature order, then consumes one selection draw.
  Choices share a scalar/vec2 type; mixed numeric choices widen to f32.
- `chance(p)` returns an i32 boolean for `unit() < p`, after evaluating p.
  It always consumes one draw; p ≤ 0 and NaN give false, p ≥ 1 gives true.
- `roll(seed, a, b)` returns a range draw from the explicit seed;
  `choose(seed, value0, …)` selects from one or more typed choices.
  Arguments evaluate in signature order before isolation; the outer stream
  is restored after the single draw. Both support named arguments.
- `noise` — smoothstep-interpolated value noise over a pinned lattice hash.
- `fault` — triangular-interpolated noise for sharp geological features.
- `color.mix`, `color.shade`, `smooth` — colour/value helpers.
- `lerp(a, b, t)` interpolates either two colors or two numbers; integer
  numbers widen to f32. Color interpolation preserves the first alpha.
- `int(x)` truncates f32 toward zero with saturation (NaN becomes zero),
  and preserves i32 values. `float(x)` widens i32 or preserves f32 values.
- `rgb(r, g, b)` / `rgba(r, g, b, a)` construct colors from integer channels
  clamped to 0–255; `rgb` uses alpha 255. Arguments run once, in signature order.
- Every builtin/canvas operation accepts named arguments. See the
  [language handbook](docs/language/index.md) and `ipc --describe-language`
  for parameter names.
- `ipc file.ips --format canonical.ips` exports canonical source during
  compilation, with deterministic formatting and executable roundtrips.
- The [recipe gallery](examples/recipes/README.md) contains 24 small,
  standalone patterns for authoring and combining procedural assets.
- Stream isolation MUST be expressible: programs may derive independent
  streams from `seed ^ constant ^ (kind · golden-ratio)` without moving a
  shared stream.

### 6.6 Determinism requirements

- Integer addition/subtraction/multiplication wrap modulo 2³²; division and
  shifts follow the pinned signed/unsigned rules and trap where specified.
- Source float values are binary32. Arithmetic, rounding and numerical
  kernels are pinned by the specifications, including binary64 intermediates
  in math/distribution kernels. Builds disable unsafe floating optimizations.
- Implicit time, thread scheduling and hardware differences MUST NOT change
  the result of a generation with identical inputs.
- The reference interpreter is the arbiter; a conformance suite (see §9)
  compares outputs across backends.

## 7. The language (`.ips`)

The complete [language handbook](docs/language/index.md) covers syntax,
typing, control flow, every builtin, composition and executable examples.
It is the authoring reference; the following section records project
features and executable examples.

The language is small, imperative and human-writable, with semantics defined
by the VM specification.

### 7.1 Requirements

- Text format with the `.ips` extension.
- An `asset` block declares the metadata from §5.3.
- Functions, locals, arithmetic, conditionals and fuel-bounded loops (`while`
  with `break`/`continue`, and `for i in a..b` sugar — both lowered to the
  VM's `br`).
- Built-in functions for the VM primitives in §6.4–6.5, including the pinned
  `sin`/`cos`, the math package
  (`abs`, `floor`, `ceil`, `min`, `max`, `pow`, `exp`, `atan2`) and the
  signed-distance fields (`dist.circle`/`dist.rect`/`dist.roundrect`/
  `dist.line`/`dist.bezier` plus `fill`). `dist.bezier(p, a, b, c)` is
  quadratic; an additional control point selects the cubic form.
  `curve(a, b, c [, d], thickness, colour)` draws either form with round
  caps; thickness is an `f32` diameter in target pixels. The noise v2 adds
  `noise.grad`/`noise.fbm`/`noise.cell`/`noise.ridge`, `warp` and
  `cell.jitter`. The curves add `gain(t, k)` and `quintic(t)`, and
  `ramp(palette, t)` interpolates a palette continuously (a compiler
  desugar over the colour/f32 lerps). The colours add `color.set.a`,
  `color.mul`, `color.scale` and `color.hsv` (the hue in turns;
  nonfinite hue shifts trap, [§12.12](spec/iprop-v0.3.md#1212-the-colours-v03)).
  The dither/fold/polar add the ordered Bayer threshold, the kaleidoscope
  symmetry and the cartesian-polar conversion. The curve toolkit adds
  `smoothstep(a, b, t)`, `remap(t, a, b, c, d)` and `clamp(t, a, b)`.
  Parts accept the D4 transforms (`mirror_x`, `mirror_y`, `rot` on the
  `part.draw` call — the exact pixel permutations, the outputs
  propagate, including writes from helper functions). Transform arguments
  are constant integers: mirrors are `0`/`1` (or `false`/`true`), and `rot`
  is `0`, `90`, `180` or `270`; rotation is applied before the mirrors.
  Each transform argument may occur once. These three names are reserved
  for part calls and cannot be declared as input uniforms. The `.ipa`
  syntax is `part.draw name [kind]`, with the optional D4 kind in `0`–`7`;
  disassembly preserves it.
  `gain` defines the `k = 1` limit;
  `ramp(palette, t)` accepts named arguments and evaluates `t` once even for a
  one-element palette ([§12.11](spec/iprop-v0.3.md#1211-the-curves-and-the-ramps-v03)).
  Pure constant ramps fold during planning; dynamic palettes use O(log N)
  selection with O(N) emitted code. Compiler expansion can reduce fuel,
  while each VM instruction keeps its specified cost.
  Sampling outside the noise primitives' defined coordinate domains traps;
  the bounds, octave checks and half-open jitter placement are specified in
  [§12.10](spec/iprop-v0.3.md#1210-the-noise-v2-v03).
- Asset-level constant arrays (`palette name = [ e, e, … ]`) with integer
  indexing. Negative or out-of-range indices select the last element; a bare
  palette name is valid only as the palette argument of `ramp`.
- Deterministic grammar with source-located parsing, typing and declaration
  diagnostics. Execution-time fuel and geometry errors are runtime traps.
- A `draw { ... }` entry block with read-only `v`/`a` builtins; the compiler
  synthesizes the runtime `(i32, i32)` parameters. Variant/archetype indices arrive as
  validated integers.
- Function parameters declare their types (`ageFromUnit(u: f32)` — `i32`,
  `f32`, `color`, `vec2` or `distribution`) and functions that return a value
  declare an explicit return type (`-> i32`). Helper calls accept positional,
  named or mixed arguments; recursion is rejected.
- `vec2.len(v)`, `vec2.dot(a,b)` and `vec2.rot(v,angle)` expose vector math.
  Positive angles in `vec2.rot`, `polar` and part rotations are counterclockwise
  in the downward-y asset plane.
- `vec2` values use `{x, y}` literals and `.x`/`.y` components, including
  points read from parts. Vectors support `+`, `-`, `*` and `/` with another
  vector, `*` and `/` with a scalar on the right, and scalar `*` vector.
  Operands are evaluated left to right, including RNG calls.
- Colors expose read-only `.r`, `.g`, `.b` and `.a` channels as `i32` bytes.
- `distribution` values describe gaussian, triangular or beta draws used by
  `lo to hi with d`; they are local/helper values, not inputs or outputs.
- `input`/`output` declarations define the asset's I/O signature: uniforms,
  and the named points, rects and circles written by `draw` (§5.4).
- `import` declarations for composition: nested parts linked at compile time,
  acyclic, with part-output access and propagation (§7.3).

Calls retain the compiler's established evaluation order: ordinary builtin
arguments run in signature order (named arguments can be reordered);
helper arguments run in parameter declaration order, including named calls;
`poly` evaluates vertex coordinates before its colour. Part calls evaluate
uniform overrides in
input declaration order, then seed/variant/archetype and placement; named
transform arguments are compile-time constants. An argument is evaluated
once, including when its result is discarded by a singleton `ramp`.

### 7.2 Sketch

Save this complete example as `rock.ips`; its seed controls the drawn
dimensions and collider:

```ips
asset Rock {
  size 32x32
  origin 16,26
  input color tint = #808d74
  output rect collider

  draw {
    w = 12 to 20
    h = 8 to 14
    oval(16, 26 - h * 0.5, w * 0.5, h * 0.5, tint)
    collider = {16 - w * 0.5, 26 - h, w, h}
  }
}
```

For composition, save the following two assets as `part.ips` and
`composition.ips` in the same directory. The child declares an origin and
an anchor:

```ips
asset Part {
  size 4x4
  origin 2,2
  input color tint = #99ddcc
  output point anchor

  draw {
    rect(0, 0, 4, 4, tint)
    anchor = {2, 1}
  }
}
```

The parent places that origin at `{8, 8}`. Its read of the anchor already
includes the child's rotation and placement:

```ips
import leaf from "part.ips"

asset Composition {
  size 16x16
  output point attached

  draw {
    leaf.draw(seed = seed, v = v, a = a, at = {8, 8}, tint = #ffcc99, rot = 90)
    attached = leaf.outputs.anchor
    pixel(int(leaf.outputs.anchor.x), int(leaf.outputs.anchor.y), #ffffff)
  }
}
```

Compile the entry asset with `ipc rock.ips -o rock.iprop` or
`ipc composition.ips -o composition.iprop`. The implemented grammar is
documented in [the language handbook](docs/language/grammar.md).

### 7.3 Imports and composition

An asset MAY be composed of smaller assets ("parts"), each authored in its own
`.ips` file. Parts let a larger asset reuse smaller generators.

- **Compile-time linking.** `import name from "file.ips"` brings a part into
  the program. The compiler merges all imported parts into a single `.iprop`;
  no imports exist at runtime, preserving self-containment (§5.3).
- **Acyclic.** Imports form a DAG; the compiler MUST reject cycles.
- **Nested instances.** A part may import its own parts. Paths resolve beside
  the importing file; each alias path is a separate instance, with at most
  256 expanded instances. A parent draws and reads only its direct children.
- **Calling a part.** The parent calls `part.draw(seed, v, a,
  at = {x, y}, uniforms...)`; seed/v/a may also be named. The part renders
  into its own sub-canvas and is blitted using the pinned alpha rule, with
  its declared origin positioned at `at` and optional D4 transforms applied.
  **Call order is paint order**, so layer stacking is deterministic.
- **Derived seeds.** Each part receives its own stream (e.g.
  `seed ^ constant-of-part`); changing one part's stream MUST NOT move the
  draws of other parts.
- **Reading part outputs.** After the call, the parent MAY read the part's
  singular outputs as `part.outputs.name`; names and types are checked at
  compile time. In format 0.5, reads include the child's transform and
  placement and are in the caller's coordinates. Host-facing outputs are in
  root asset coordinates. Frozen 0.1–0.4 files retain their local output
  coordinates; list outputs cannot be read as source expressions.
- **Propagation.** The parent MAY assign a part's output to one of its own
  declared outputs, so a child's computed anchor surfaces in the final
  `outputs` map of the composed asset.
- **Determinism.** Part outputs depend on their supplied inputs, selectors,
  transforms and placement. The conformance suite compares the merged
  program as a whole — pixels and every structured output (§9).

## 8. Backends (interpreters)

All backends execute the same validated bytecode. The reference CPU
interpreter is authoritative for correctness.

| Backend | Technology | Current role |
| ------- | ---------- | ---------- |
| reference | C++20 | Authoritative CPU interpreter; conformance arbiter |
| capi | C99 + C++20 | The stable C API (`ipropc`); the foundation for every native host |
| html5 | Emscripten/WASM | Browser execution of the website's live examples |
| sfml | C++20 + SFML 3.1 | Native desktop host; `sf::Image` output |
| godot | GDExtension over the C API | Engine integration: `IpropAsset`/`IpropSprite2D` |

- SFML and Godot are optional CMake integrations: `AUTO` builds them when
  dependencies are available, `ON` requires them and `OFF` excludes them.
- Dedicated OpenGL and Vulkan hosts are planned; no implementations ship in
  this checkout. The intended role is CPU generation followed by GPU texture
  upload and presentation.
- OPTIONAL future work: detect a restricted "pure per-pixel" subset and lower
  it to GLSL/SPIR-V for hot paths. The reference interpreter remains
  authoritative.
- Backends SHOULD support rendering at a requested size where the program
  permits (resolution independence).

## 9. Conformance suite

- Golden PNGs for a corpus of programs and complete generation inputs,
  generated by the reference interpreter.
- Conforming backends reproduce every RGBA byte exactly, including RGB under
  transparent pixels; there is no image tolerance.
- Structured outputs (computed colliders, anchor points) are compared exactly
  as part of the same corpus.
- GitHub CI runs on demand (`workflow_dispatch`) and from the release workflow
  for pushed release tags; ordinary pushes and pull requests do not start it.
- Frozen binaries retain their images, output bits, traps, RNG and fuel
  behavior. Intentional source-language migrations are documented separately
  and asserted explicitly by the runtime compatibility matrix.
- The corpus MUST exercise raster primitives, seeded generation, composition
  and structured outputs.

## 10. Compiler toolchain

- Pipeline: parse/import/type-check → plan calls/effects → lower/assemble →
  optimize → validate → apply debug/compression policy.
- Production output is optimized, debug-stripped and compressed when smaller.
  `--debug` keeps source maps/symbols; `--no-opt` and `--no-compress` select
  inspection modes.
- `ipc file.ips --check --diagnostics=json` checks without writing files;
  `ipc file.ips --format canonical.ips --format-only` writes only validated
  canonical source. Formatting preserves comments and executable meaning.
- Six CLI tools: `ipc` (compiler), `ipa` (assembler), `ipdis`
  (disassembler), `ipval` (validator), `ipgen` (renderer) and `ipsheet`
  (variant/seed sheets).
- `ipc --describe-language` exports schema-3 language contracts, including asset
  constant policy and builtin constant-evaluation eligibility; JSON
  diagnostics use schema 1. Generated documentation includes `LLM_REFERENCE.md`.
- Repeated compiles with the same compiler, source/imports and options produce
  identical executable bytes.

Build and run the tools from the repository root (Windows adds `.exe`):

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
build/tools/ipc examples/language/first-asset.ips -o build/first-asset.iprop
build/tools/ipval build/first-asset.iprop
build/tools/ipgen build/first-asset.iprop --seed 7 -o build/first-asset.png
```

The native build requires CMake 3.24+, a C++20/C99 toolchain and zlib 1.2.9+.
Tests fetch Catch2 by default. Python 3.10+ enables handbook generation;
release packaging requires Python 3.12+. Native SDKs contain the tools in
`bin/` and documentation/examples under `share/iprop/`.

```
  backends/    # html5 (Emscripten), capi (the stable C API), sfml, godot
  editor/      # VS Code authoring extension
  website/     # Static site, live WASM examples and generated documentation
  docs/        # Language handbook, integration contracts and release notes
  examples/    # .ips sources + compiled .iprop files
  tests/       # Golden images and conformance suite
  benchmarks/  # Measurements and frozen runtime baselines
  cmake/       # Build, ABI and installation configuration
  scripts/     # Documentation, compatibility checks and release packaging
```

**Version milestones.** v0.1.0 introduced the format, VM, language and
HTML5 backend. v0.2 rounded out the language — typed
function signatures, the pinned trig and math packages, constant arrays
(palettes) and loop control — and added native backends on the C API:
the SFML window and the Godot GDExtension, each with its own conformance.
v0.3.0 added vectors, distance fields, curves, procedural noise, colour
utilities and exact part transforms. v0.4.0 added named calls, RNG sugar,
canonical formatting, Unicode diagnostics, 24 recipes, the complete language
handbook, bit-exact compiler optimizations and lossless compression. v0.5.0
added signed defaults, `ipc --check` with JSON diagnostics, named helper/part
arguments, comment-preserving formatting, the language export and
`LLM_REFERENCE.md`, and C API 0.3: reflection, parameter sets, structured
errors, image views and typed output reads. v0.6.0 added color channel reads,
`lo to hi` random ranges over numbers, colors and `vec2` segments, the
`distribution` type with gaussian, triangular and beta shapes, and nested
parts whose outputs read in the caller's coordinates. Product 0.6.0, source
language 0.6, format 0.5 (with frozen 0.1–0.4 reader compatibility), C API
0.3 and ABI line 0.4 are separate contracts; the API 0.2 layouts are
unchanged. Migration and release commands are in
[the 0.6 notes](docs/release-v0.6.md).
The current 0.7 development adds exact integer bounds and scaled binary64
`vec2.normalize`, plus typed asset constants with compile-time dependency and
distribution validation; see [0.7 migration](docs/language/migration-v0.7.md).
The tagged release workflow builds, validates and publishes source, native
SDK, WASM and website packages. The same packages can be built locally.
GitHub CI checks the native toolchain/C API, editor contracts, WASM, website,
SFML and Godot, with separate sanitizer checks. Deployment of the website
and distribution of the editor extension are separate from release packaging.

Current demonstrations include the [24 recipes](examples/recipes/README.md),
[0.6 random-feature previews](examples/previews/README.md), the nested
mushroom colony in `examples/colony/` and the separately licensed website
showcase. Additional, unimplemented example ideas include:

- **Butterfly (512×512):** one wing part placed four times using D4 transforms;
  seeded SDF silhouettes, Bezier veins and antennae, `fold` symmetry,
  `hsv`/`ramp` palettes, `cell.jitter` eyespots, `fbm` mottling and dither shading.
- **Bob Ross landscape:** ramp skies, ridge/fbm mountains with atmospheric
  perspective, jittered trees, folded water reflections, mist and seed-selected
  biomes with their own palettes.

Future work includes general affine part transforms with pinned resampling,
masks and multiple rendering passes, full colour arithmetic, `switch`, and
Bevy/Unity integrations. Whole-canvas generators such as diamond-square and
cellular automata depend on the future buffer/mask work. L-systems and a
dedicated noise-graph DSL remain outside the language scope; user functions,
`warp` and curve builtins cover functional noise composition.

Validate a local package from a clean, committed checkout. A complete 0.7
release requires the remaining stages and a frozen format specification:

```sh
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release --parallel
scripts/release.sh 0.7.0 build-release --check
```

Use `IPROP_SFML=ON` and `IPROP_GODOT=ON` with their dependency paths when
including those integrations; required mode fails on missing dependencies.
Godot packages require `GODOTCPP_TARGET=template_release`. The script
validates CTest, a moved installation, all six tools and external shared/static
C API consumers before writing versioned source/native archives and SHA-256
checksums when packaging is requested.
The native archive records its source commit, included backends and the
independent `product_version`, `language_version`, `format_version`,
`c_api_version` and `c_abi_soversion` in `release.json`; packaging rejects an
installed compiler whose export differs from these source versions. A tagged
release requires the frozen specification of the emitted format, not one named
after the product. Pass `--check` to validate an in-progress build without
creating archives. Build the current WASM module and website before running
`python3 scripts/package_web.py` to create their separately validated
archives; `website/README.md` records the build sequence. Publication is
handled by the tagged release workflow.

In a cloud-synchronized checkout, add
`-DIPROP_LANGUAGE_DOCS_DIR=/absolute/path/language-docs` to the CMake configure
command if generated handbook copies conflict. Choose a directory outside
synchronization; the website accepts `IPROP_LANGUAGE_DOCS_DIR` as an
environment variable.
See [documentation and artifact checks](docs/ci.md).

Compiler optimization checks and measured reductions are recorded in
[the v0.4 acceptance report](docs/optimization-acceptance-v0.4.md).
The [v0.6 runtime matrix](docs/optimization-acceptance-v0.6.md) records the
previous release's source and frozen-binary compatibility. The
[0.7 stage 1 gates](docs/language/migration-v0.7.md#validation-scope) extend
that coverage with exact math and preserved pre-change bytes; the
[stage 1 validation report](docs/validation-v0.7-stage1.md) records the results.
The [stage 2 validation report](docs/validation-v0.7-stage2.md) covers asset
constants, contextual names, compiler diagnostics and host conformance.

The current runtime supports formats 0.1–0.6 and the
[lossless DEFLATE container](spec/iprop-v0.4.md) introduced in 0.4. A compressed
container retains a 0.4 outer header even when its inner executable is 0.6.
`ipc` strips debug information by default and
compresses only when the complete output is smaller. Use `--debug` to keep
source maps and symbols, and `--no-compress` for an expanded file; either
choice preserves execution. `--debug` and `--strip` use the last flag given.
Low-level layout/section
inspection uses `decompressFile` or `LoadedFile::bytes()`. Native builds and
installed CMake consumers require zlib 1.2.9 or newer; the Emscripten build uses
its pinned zlib port via `-sUSE_ZLIB=1`.
