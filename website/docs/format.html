The .iprop format

A self-contained binary: one file carries the metadata, the constants and the bytecode — no external resources. The canonical specification is spec/iprop-v0.4.md in the repository; this page summarises it.

Format 0.4 adds lossless zlib/DEFLATE containers and accepts frozen 0.1–0.3 files. The vector, distance, noise, colour and D4 contracts inherited from 0.3 remain unchanged; instructions and value types introduced by a later format version are rejected in earlier files.

The file layout

An expanded 0.4 file retains the existing layout:

header (20 bytes)          magic "IPRP", version 0.4, flags, section count
section table (12 bytes × N)   id, offset, size
sections                    meta · const · code · debug (optional)
  • All multi-byte values are little-endian; sections are 4-byte aligned.
  • The header flag bit 0 marks the debug section (spec §7); the validator rejects a flag/section mismatch.
  • Header flag bit 1 selects compression only in minor 4. After its 20-byte header are the expanded size (u32) and one zlib stream containing the complete original file, including its header/table. Both encoded and expanded files are bounded to 64 MiB; checksum, exact length, trailing data, dictionaries and nesting are checked before execution.

ipc strips debug data and packs only when smaller by default. Use --debug to retain source maps, --no-compress for expanded inspection, or --no-opt for reference compiler lowering. These switches preserve successful image/output bits. The runtime owns the expanded bytes for the lifetime of code/debug views.

The sections

sectioncontents
metathe canvas size, the origin, the declared variants/archetypes, the fuel budget, the input uniform entries (type, name, default) and the output slot entries (kind, list flag, name)
constdeduplicated pools: strings, i32, f32 and colours — every instruction references them by index
codethe function table (names, signatures, locals, stream offsets) followed by the concatenated instruction streams (4 bytes per instruction: opcode, aux, u16 operand) and the part table
debuginformative: per function, the local names and the source line of every instruction (§7); stripping it must not change execution

Function 0 is the entry point draw with parameters (i32 variant, i32 archetype) followed by one parameter per uniform. The instruction set (spec §9) covers control flow, the operand stack, integer/float/colour/vector arithmetic, the pinned seeded primitives, the canvas raster operations, the structured outputs and part calls.

Determinism

  • Generation is a pure function of the inputs: identical inputs produce identical images and outputs — bit-exact, across platforms and backends.
  • The seeded primitives are specification-pinned instructions (not library calls): the splitmix32 hash, the Weyl-sequence stream, the value/fault noise — every operation's exact algorithm is written down (spec §11–§12).
  • The colour helpers pin the fused-multiply-add behaviour, so compiled code matches the reference builds bit for bit.
  • Every execution runs under a fuel budget (meta.fuel), which guarantees termination.
  • A golden corpus of (program, seed) images is committed; any compiler or interpreter change that alters a golden image is a breaking change.
