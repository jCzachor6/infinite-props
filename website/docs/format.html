The .iprop format

One self-contained binary: metadata, constants and bytecode, with no external resources.

Format {{FORMAT_VERSION}} · released with product {{PRODUCT_VERSION}}

This page summarises the format. The canonical contract is the specification: iprop-v{{FORMAT_VERSION}}.md, which inherits 0.5 and takes precedence over it. The frozen 0.1, 0.2 and 0.3 specifications stay available.

Versions

Format 0.5 adds colour channel reads, uniform random ranges, distributions, gradients and segments, and named part instances whose outputs arrive in the caller's coordinates. An interpreter for 0.5 still accepts every 0.1–0.4 file under its original rules.

Format 0.6 is the development contract for product 0.7.0. Stage 1 adds exact signed integer min/max/clamp and stable vector normalization. The runtime reads 0.1–0.6; existing mathematical and host output contracts remain frozen. Later 0.7 features are not implemented by this stage. Stage 2 adds typed asset constants evaluated by the compiler through existing runtime operations; scalar constants introduce no new binary layout or host interface. Stage 3 adds parameterized type descriptors, immutable collection pools and list instructions, including poly(list<vec2>, color). Stage 4 adds captured sampler<T> descriptions, .pick() and immutable .pick(n) batches, using the existing range/RNG algorithms. Descriptors can also reference sampler elements in lists. Stage 5 adds constant sampler pools, const lists of descriptions and compile-time range palettes with explicit picks. Direct palette indexing keeps its fallback; first-class list indexing checks bounds. Weighted/density distributions and surfaces remain pending; public host layouts remain unchanged.

  • The compiler and assembler write the oldest minor that holds the file, never older than 0.4: a file retaining a new math instruction needs 0.6, while 0.5 instructions or parts need 0.5. Folded constants do not force a newer version.
  • The compressed envelope remains a 0.4 container. Its inner file may have any supported version, 0.1–0.6; a 0.5 interpreter rejects an inner 0.6 file by its version after expansion.
  • Instructions and sections introduced by a later minor are invalid in an earlier file, including in unreachable code.

The file layout

header (20 bytes)              magic "IPRP", version, flags, section count
section table (12 bytes × N)   id, offset, size
sections                       meta · const · code · debug (optional) · parts (0.5) · types / collections (0.6)
  • All multi-byte values are little-endian; sections are 4-byte aligned.
  • Header flag bit 0 marks the debug section; the validator rejects a flag/section mismatch.
  • Header flag bit 1 marks a packed file (minor 4 headers only). After the 20-byte header come the expanded size (u32) and one zlib stream holding the complete original file. Encoded and expanded files are bounded to 64 MiB; the checksum, exact length, trailing data, dictionaries and nesting are checked before execution.

ipc strips debug data and packs only when that is smaller. Use --debug to keep source maps, --no-compress for an expanded file and --no-opt for the reference lowering; none of them changes the image or output bits.

The sections

sectioncontents
metathe canvas size, the origin, the declared variants and archetypes, the fuel budget, the input uniforms (type, name, default) and the output slots (kind, list flag, name)
types / collectionsformat 0.6 descriptors and immutable list data; helper values share arena handles
constdeduplicated pools of strings, i32, f32 and colours, referenced by index
codethe function table (names, signatures, locals, offsets), the instruction streams (4 bytes per instruction: opcode, aux, u16 operand) and the part table
debuginformative: local names and the source line of every instruction; stripping it never changes execution
parts0.5: one entry per part instance with its name (the import alias path, such as hilt.grip) and its parent, forming the tree that maps outputs into caller coordinates

Function 0 is the entry point draw with parameters (i32 variant, i32 archetype) followed by one parameter per uniform.

The virtual machine

  • A stack machine with locals and calls, and structured control flow only: block, loop, if/else, br, br_if.
  • Branches depend on integers only; floats are for geometry and colour.
  • Every instruction spends fuel from the budget declared in meta; running out aborts with a defined error, so every file terminates.
  • The only mutable state is the canvas, the declared outputs, the stack and the locals. Every canvas write is bounds-checked.

Determinism

  • Generation is a pure function of its inputs: the same file, seed, variant, archetype, size and uniforms give the same image and outputs, bit for bit, on every platform and backend.
  • The seeded primitives are specification-pinned instructions, not library calls: the splitmix32 hash, the Weyl-sequence stream, value and fault noise, and the binary64 kernels behind the distributions.
  • Colour helpers pin their fused-multiply-add behaviour, so compiled code matches the reference builds exactly.
  • A committed golden corpus of (program, seed) images guards the pipeline: changing a golden pixel is a breaking change.
